# Assistant LLM intégré au VBE

Cette première tranche ajoute une fenêtre de conversation WinForms au complément COM. Elle s'ouvre avec le VBE et tente d'être possédée par sa fenêtre principale via `MainWindow.HWnd`. L'assistant appelle directement `VbeSession`, sur le thread UI du VBE, sans serveur MCP, raccourci clavier ni coordonnées de fenêtre. Le menu natif **Affichage > Assistant CodexVBE** permet de rouvrir cette fenêtre ; **Outils > Configuration CodexVBE** ouvre les réglages.

## Fournisseurs

| Choix dans la fenêtre | État | Configuration avant lancement d'Excel ou SOLIDWORKS |
| --- | --- | --- |
| Codex (par défaut) | Implémenté via `codex app-server` local et l'authentification ChatGPT déjà gérée par le CLI | État ChatGPT et bouton de connexion dans Configuration ; aucune clé API requise. |
| OpenAI API | Implémenté via Chat Completions | Clé et URL dans Configuration ; `OPENAI_API_KEY` et `CODEXVBE_OPENAI_ENDPOINT` restent des valeurs de secours. |
| Ollama | Implémenté via son endpoint compatible Chat Completions | URL dans Configuration ; défaut `http://localhost:11434/v1/chat/completions`. |
| Claude | À venir | L'API et l'authentification Claude ne sont pas implémentées. |
| GitHub Copilot | À venir | L'authentification et l'API Copilot ne sont pas implémentées. |
| Gemini | À venir | L'API et l'authentification Gemini ne sont pas implémentées. |

Les URL distantes doivent utiliser HTTPS ; seul HTTP sur une adresse de boucle locale est accepté. Les réglages non secrets sont enregistrés pour l'utilisateur Windows dans `%APPDATA%\CodexVBE\settings.json`. Une éventuelle clé OpenAI API y est stockée uniquement sous forme chiffrée DPAPI `CurrentUser`, jamais dans le dépôt. Codex ne lit, ne copie et ne stocke aucun jeton OAuth : seul le processus `codex app-server` gère la connexion ChatGPT existante. La liste des modèles vient du fournisseur actif (`model/list`, `/v1/models` ou `/api/tags`) ; le choix persiste par fournisseur et s'applique au prochain message. Codex affiche aussi les niveaux de raisonnement annoncés pour le modèle choisi ; le niveau retenu est transmis comme `effort` au prochain `turn/start` et mémorisé par modèle. Changer de fournisseur efface l'historique affiché et le contexte transmis au modèle. Un modèle Ollama doit lui-même prendre en charge les appels d'outils pour piloter le VBE. Le catalogue OpenAI peut inclure des modèles qui ne prennent pas en charge Chat Completions ou les outils ; l'API signale ce cas lors de l'envoi.

Le client Codex initialise app-server par JSONL sur stdin/stdout, vérifie `account/read` avec `type: chatgpt`, crée un thread éphémère, puis transmet les commandes VBE comme `dynamicTools` (API expérimentale). Les appels `item/tool/call` retournent les résultats de `VbeSession` ; les demandes d'édition suivent la politique choisie dans Configuration. Un éventuel appel serveur inconnu reçoit une erreur explicite. Le choix de Codex ne passe pas par l'API OpenAI payante. Le contexte développeur précise l'identité CodexVBE, l'hôte VBE sans supposer Excel, l'inspection avant action, le ciblage et les révisions. `status` fournit à la demande le processus hôte et les projets courants ; aucun inventaire n'est joint automatiquement à chaque message.

## Opérations proposées au modèle

La lecture `form_tree` parcourt les conteneurs et fournit un chemin canonique pour chaque contrôle, Page et Tab. `FormVersion` et `TreeVersion` désignent la même empreinte récursive des chemins et propriétés. `add_nested_form_control`, `set_form_node_property` et `set_form_node_picture` prennent cette empreinte avant une écriture. La commande de propriété utilise le descripteur typé réel, avec conversion de couleur et d'énumération ; la commande d'image charge localement Picture ou MouseIcon quand le descripteur annonce un objet image modifiable. Les propriétés déclarées en lecture seule et les objets sans membre COM modifiable produisent une erreur explicite. Dans Excel jetable, l'arbre des Frame/MultiPage/TabStrip, la version stable, Caption, largeur, couleur, enum, Font.Name, Page.Caption, Tab.Caption et Picture d'un Label imbriqué ont été relus après modification. Ces essais ne prouvent pas encore l'écriture de chaque descripteur inventorié.

`list_form_control_types` réunit les 14 ProgID Forms natifs et les ProgID x64 installés déclarant CATID_Control dans le registre COM. Pour les contrôles additionnels, ce catalogue indique seulement une candidature : `Controls.Add` doit confirmer que le VBE de l'hôte accepte réellement le contrôle. Aucune compatibilité ActiveX additionnelle n'est déduite du registre seul.

Dans un Excel jetable, le catalogue a retourné 14 contrôles Forms natifs et 12 candidats CATID_Control. Le premier essai d'un `MSComctlLib.ListViewCtrl.2` a été refusé par le conteneur VBE (« Le sujet n’est pas approuvé pour l’action spécifiée ») sans terminer Excel ; les autres candidats n'ont pas été essayés.

`project_properties` et `component_properties` lisent les propriétés COM exposées, les composants et les empreintes. Les opérations `set_project_property` (hors `Name`), `set_component_property`, `rename_component`, `remove_component`, `import_component` et `export_component` utilisent le mode conception et les révisions de projet/composant ; l'import/export exige un chemin absolu fourni explicitement. Le renommage du projet est désactivé : un essai Excel a été suivi d'un crash du processus (`0xc0000374`), sans cause exacte encore établie. Excel a confirmé le refus de `rename_project` et de `set_project_property Name` avant tout appel COM, le refus de supprimer un composant document Type 100, et un cycle complet d'export/suppression/import d'un module standard `.bas` avec code restauré exactement. Les cycles classe et UserForm n'ont pas été vérifiés.

`vbe_windows` et `code_panes` lisent les collections VBIDE natives, la fenêtre active et le volet de code actif. La lecture des volets passe par `VBE.CodePanes`, car le getter `VBComponent.CodePane` peut créer et activer une fenêtre. Les index retournés servent seulement au diagnostic instantané ; les identités de projet, de module et les titres de fenêtre doivent être relus avant une action. Dans Excel, `vbe_windows` a compté sept fenêtres avant puis huit après l'ouverture d'un module ; `code_panes` est passé de zéro à un, avec projet, module et sélection exacts. Le getter `Docked` n'existe pas sur l'objet Window de cet hôte et a été retiré ; l'état d'ancrage reste à déterminer par `LinkedWindows` lors d'une autre sonde. Références : [collections VBIDE](https://learn.microsoft.com/en-us/office/vba/language/reference/visual-basic-add-in-model/collections-visual-basic-add-in-model) et [propriétés VBIDE](https://learn.microsoft.com/en-us/office/vba/language/reference/visual-basic-add-in-model/properties-visual-basic-add-in-model).

`select_code_range` sélectionne plusieurs lignes par quatre coordonnées natives et un SHA de module actuel. Dans Excel, une sélection de deux lignes a été relue à l'identique ; la plage inversée et le SHA périmé ont été refusés. `show_vbe_window` réaffiche une fenêtre permanente masquée ciblée par titre et type exacts ; `window_linkage` lit son `LinkedWindowFrame` et les fenêtres liées, sans les déplacer. Dans Excel, l'Explorateur d'objets a été masqué puis réaffiché, et quatre fenêtres liées ont été relues dans le cadre de l'Explorateur de projets. La modification de l'ancrage n'est pas encore exposée.

`read_vbe_options` ouvre le dialogue natif Outils > Options, lit les contrôles visibles des onglets Éditeur, Format de l'éditeur, Général et Ancrage par UI Automation, puis ferme avec Annuler. Deux lectures successives en Excel ont rendu 26 cases et radios stables. Les valeurs indisponibles restent nulles ; aucune commande de modification des options n'est encore exposée.

La commande `open_object_browser` recherche le contrôle natif VBE `Id=473`, activé et identifié par sa légende « Explorateur d'objets » ou « Object Browser », puis invoque `CommandBarControl.Execute`. Elle retourne `WindowsBefore` et `WindowsAfter` depuis `vbe_windows` ; une fenêtre visible `Type=2` (`vbext_wt_Browser`) confirme seulement l'ouverture. Essai Excel réel : le premier appel a rendu `Executed=true`, `Verification=Pending` avec 0 fenêtre Browser dans les deux clichés immédiats ; un appel distinct `vbe_windows` a ensuite vu `Type=2`, visible et actif. Un second appel a rendu `AlreadyVisible=true`, `Verification=Visible`. L'outil LLM suit cette lecture différée. Une sonde externe a séparément sélectionné `Excel.Application.ActiveWorkbook` dans la fenêtre native et lu son détail via UIA ; cette preuve ne donne pas encore un lecteur structuré fiable dans le complément (thread et latence à concevoir). [Enum vbext_WindowType](https://learn.microsoft.com/en-us/dotnet/api/microsoft.vbe.interop.vbext_windowtype?view=office-pia), [Explorateur d'objets Visual Basic](https://learn.microsoft.com/en-us/windows/win32/com/visual-basic-object-browser).

Prototype en lecture seule, exposé au LLM après l'essai Excel : `list_reference_types(Project, Guid, Major, Minor, Offset, Limit)` et `list_type_members(Project, Guid, Major, Minor, TypeIndex, TypeIdentity, Offset, Limit)`. La référence doit être sélectionnée dans `VBProject.References` et son GUID/version correspondre exactement. Le lecteur ouvre son `FullPath` par `LoadTypeLibEx(REGKIND_NONE)` sans enregistrer la bibliothèque ; si ce chargement échoue, `LoadRegTypeLib` reprend l'identité enregistrée et la réponse indique `Source=RegisteredTypeLibrary` avec l'erreur initiale. La typelib chargée est revalidée par GUID/version. Chaque page contient au plus 50 entrées ; les erreurs COM par type/membre sont rapportées avec HRESULT. `TypeIdentity` lie l'index à la référence et aux métadonnées du fichier pour éviter de viser un autre type au second appel. Pour les coclasses, `list_type_members` lit l'interface non source par défaut ; les choix de filtrage de l'Explorateur natif ne sont pas reproduits. `VBAProject` affiché comme bibliothèque dans l'Explorateur est le projet courant, pas une référence de `VBProject.References`, et reste hors de ces commandes.

Essai Excel réel : la typelib Excel contient 1036 types ; une page `Offset=1030, Limit=6` a renvoyé `Application` en coclass à l'index 1030. Son `TypeIdentity` a permis de lire l'interface `_Application` : 474 membres COM bruts, première page de 20 comprenant notamment les entrées IUnknown/IDispatch et `Application`, `Creator`, `ActiveCell`. `ActiveWorkbook` est à l'index membre 18, `INVOKE_PROPERTYGET`, DISPID 308 ; l'Explorateur natif lu séparément par UIA affiche `Property ActiveWorkbook As Workbook / Lecture seule / Membre de Excel.Application`. Dans ce processus, la référence VBA expose 46 types et stdole 42. La typelib Office a donné 521 types par `LoadTypeLibEx` directement dans ce processus. Une sonde PowerShell extérieure avait au contraire reçu `TYPE_E_CANTLOADLIBRARY` pour MSO.DLL puis réussi par `LoadRegTypeLib` ; le repli n'est donc pas encore validé in-process. [LoadTypeLibEx](https://learn.microsoft.com/en-us/windows/win32/api/oleauto/nf-oleauto-loadtypelibex), [ITypeLib](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.comtypes.itypelib?view=netframework-4.8.1), [ITypeInfo](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.comtypes.itypeinfo?view=netframework-4.8.1).

`import_component` compare désormais les composants avant/après l'appel `VBComponents.Import`. L'appel n'est jamais répété automatiquement : un HRESULT d'erreur peut suivre l'ajout effectif du composant. La réponse sépare `Applied`, `Verified` et `VerificationPending` et restitue les erreurs de relecture. Dans Excel, un UserForm avec Label a été exporté en `.frm`/`.frx`, supprimé puis importé : `Applied=true`, `Verified=false` et `ComponentReadbackError=E_FAIL`, tandis que la relecture dans un appel séparé a retrouvé le même SHA de code, le même arbre et la même version. `VerificationPending=true` désigne alors une vérification différée, pas un échec de l'import. Trois tentatives immédiates dans le même appel avaient toutes échoué ; elles ont été retirées pour éviter de bloquer le VBE. Quand la vérification est en attente, la commande invite à appeler `component_properties` et `project_properties` séparément avant toute autre mutation. Si le nombre de nouveaux composants est ambigu, elle demande `list_modules` avant toute nouvelle tentative.

`list_procedures` énumère les procédures d'un module avec `ProcOfLine`, `ProcStartLine`, `ProcBodyLine` et `ProcCountLines` ; les Property Get/Let/Set gardent un `ProcKind` distinct. Dans Excel, une classe de 19 lignes a renvoyé un Sub, une Property Get, une Property Let et un autre Sub aux lignes attendues ; `select_procedure` a ciblé la déclaration du Get et refusé un SHA périmé. La première version de `find_code` utilisait `CodeModule.Find`, mais échouait sur deux occurrences d'un même mot dans une ligne à cause des bornes COM modifiées entre deux appels. La commande lit maintenant `CodeModule.Lines` et recherche chaque occurrence en mémoire, avec options casse/mot entier, maximum 200 positions et SHA de chaque source. `PatternSearch` interprète `*` et `?` sur une seule ligne ; un motif constitué uniquement d'astérisques est refusé. Dans Excel jetable PID 28032, la recherche littérale et celle avec `?` ont chacune trouvé quatre positions ; le motif sensible à la casse en a trouvé une. L'itération native de `Find` reste à diagnostiquer. Références : [CodeModule](https://learn.microsoft.com/en-us/dotnet/api/microsoft.vbe.interop._codemodule?view=office-pia) et [Find](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/find-method-vba-add-in-object-model).

`inspect_code_file` lit uniquement les octets d'un chemin absolu fourni par l'utilisateur. Il retourne BOM, validité UTF-8 stricte, présence d'octets non ASCII ou NUL, SHA-256 et page de code ANSI de l'hôte, sans exposer le contenu. `insert_code_file` exige ce chemin, le SHA courant du module, une ligne d'insertion et le mode conception. Un fichier ASCII ou muni d'un BOM reconnu est décodé directement ; un fichier sans BOM contenant des octets non ASCII exige `SourceEncoding` explicite (`utf-8`, `utf-16le`, `utf-16be`, `windows-1252` ou `system-ansi`). Le complément ne déduit pas l'encodage d'une extension ou d'un UTF-8 seulement valide. Il lit au plus 256 Kio, retourne le SHA des octets source et celui du code inséré, et vérifie les caractères non ASCII après insertion dans le VBE. La consigne et la page de code courante sont recalculées dans le message système du fournisseur et dans le contexte de chaque tour, y compris après reprise d'une conversation Codex. Dans Excel jetable PID 31092, l'absence d'encodage explicite a été refusée, puis « é » a été conservé en UTF-8 et Windows-1252 ; un SHA de module périmé a été refusé. Compilation et persistance restent des vérifications séparées.

`remove_form_control` exige un chemin `form_tree` finissant par `Controls/<nom>` et une `ExpectedTreeVersion`, appelle `Controls.Remove` sur le conteneur exact puis vérifie que le chemin a disparu et que l'empreinte a changé. Dans Excel jetable, les suppressions d'un Label racine, dans Frame et dans MultiPage Page ont chacune renvoyé `Applied=true`, réduit le compte des nœuds et changé l'empreinte ; Excel est resté vivant. Une version périmée et un chemin Page ont été refusés sans mutation. La commande est maintenant offerte au LLM sous la politique d'approbation des écritures. La [documentation Microsoft Forms](https://learn.microsoft.com/en-us/office/vba/Language/Reference/User-Interface-Help/remove-method) avertit que certains contrôles ajoutés en conception peuvent refuser `Remove` ; les essais ne couvrent que ces trois Labels créés par le complément. `TabIndex` est déjà accessible par `set_form_node_property`. `ZOrder` n'est pas encore exposé : la [méthode officielle](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/zorder-method) ne change pas l'ordre de la collection Controls et l'empreinte actuelle ne prouverait pas son effet.

`z_order_form_control` est exposé au LLM sous la politique des écritures VBE. Il exige un chemin canonique de contrôle, le mode Conception, une `ExpectedTreeVersion` actuelle et `ZPosition=0` (devant) ou `1` (derrière). La commande relit la présence du contrôle mais renvoie `Verification=Unverified`, car la méthode MSForms `ZOrder` ne modifie pas l'ordre de `Controls` et `form_tree` ne stocke pas la superposition. La sonde `tools/probes/Test-ZOrder.ps1` a créé deux Labels opaques superposés dans Excel PID 12236 et capturé trois PNG : avant (bleu devant), rouge devant, rouge derrière (bleu devant). Excel est resté vivant et `TreeVersion` n'a pas changé. Cette preuve visuelle valide l'effet de l'API sur ces deux Labels ; elle ne rend pas l'ordre relisible par VBIDE. [Microsoft Forms ZOrder](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/zorder-method).

La première sonde de duplication générique a échoué dans Excel PID 47340 sur `Label.Cancel` : le descripteur l'annonçait modifiable, mais `SetValue` a rendu « Membre introuvable ». Le processus s'est ensuite arrêté ; le journal Windows signale `ntdll.dll`, `0xc0000374` (corruption mémoire). La corrélation est forte, sans preuve que ce seul setter soit la cause du crash. La route `duplicate_leaf_form_control` et son prototype source ont été retirés. `SetNodeProperty` refuse désormais `Label.Cancel` avant d'appeler COM. Aucun nouvel essai de ce setter n'est prévu.

`duplicate_form_label` est une sonde bridge limitée au Label natif, sans exposition LLM. Elle copie seulement Name, Caption, Left/Top/Width/Height, BackColor et Font.Name/Size/Bold, relit les valeurs et marque le résultat `Completeness=Partial`. `Test-LabelDuplication.ps1` a validé deux fois dans Excel jetable la création d'un second nœud, le changement de `TreeVersion` et un processus toujours vivant (PID 3724 et 48020). Les autres propriétés ne sont pas copiées. `form_property_accessors` lit les accesseurs ITypeInfo sans écrire : sur le Label réel, `Cancel`, `Caption` et `BackColor` déclarent tous `PROPERTYGET` et `PROPERTYPUT`, y compris le setter Cancel qui a échoué au runtime. Pour Font.Name, IProvideClassInfo est indisponible. Ces métadonnées ne prouvent donc pas que le setter fonctionne ; seules les mutations ciblées relues dans Excel peuvent élargir la liste.

`add_form_page`, `add_form_tab` et `remove_form_page_tab` sont maintenant offerts au LLM sous la politique d'écriture. Elles ciblent le parent ou l'élément par chemin canonique, demandent `ExpectedTreeVersion`, utilisent `Pages.Add`/`Tabs.Add`/`Remove` puis relisent l'arbre. `InsertIndex` facultatif (base zéro) permet une insertion à une position précise. Dans Excel, les deux ajouts à l'index 1 ont donné l'ordre attendu ; `Remove(index)` a ensuite retiré la Page et le Tab avec compte et ordre relus. `Tabs.Remove(name)` avait été refusé par le conteneur, d'où la résolution de l'index numérique. `set_form_node_property Index=0` sur Page2 puis Tab2 a réordonné chaque collection, avec changement de `TreeVersion` et relecture. Un cycle Page antérieur avait une version finale différente malgré l'ordre restauré ; le cycle suivant est revenu exactement à la version initiale. Il faut donc relire les propriétés et la sélection à chaque action, pas présumer la réversibilité bit à bit. Les [méthodes Microsoft Forms](https://learn.microsoft.com/fr-fr/office/vba/language/reference/user-interface-help/add-method-microsoft-forms) documentent ces collections.

`create_event_procedure` est maintenant offert au LLM sous la politique d'écriture. Elle cible un UserForm en mode conception, vérifie `ExpectedSha256` du code et `ExpectedTreeVersion` du concepteur, exige un `ObjectName` existant dans l'arbre (ou `UserForm`), refuse le nom de procédure déjà présent, appelle `CodeModule.CreateEventProc(EventName, ObjectName)` puis relit le nom et le SHA. Dans Excel jetable, `Click` sur `cmdProbe` a créé `Private Sub cmdProbe_Click()` ligne 1, puis `Initialize` sur `UserForm` a créé `UserForm_Initialize` ligne 5 ; `list_procedures` a relu les deux stubs. Doublon, événement inexistant et cible absente ont été refusés sans changer le SHA. [Référence Microsoft VBIDE](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/createeventproc-method-vba-add-in-object-model).

`invoke_debug` conserve le ciblage par projet/module/SHA/ligne et contrôle natif. Il lit `debug_state` juste avant et juste après `CommandBarControl.Execute`. Le résultat distingue `Executed` (la méthode native a été invoquée) de `Verification=Verified` lorsqu'un changement de mode ou de position de code est effectivement observé, et `Unverified` sinon. Dans Excel, `run`, `step_into` et `continue` ont tous rendu `Unverified` immédiatement ; un appel distinct à `debug_state` a ensuite confirmé respectivement le point d'arrêt, la ligne suivante et le retour au mode conception. Le VBE traite ces commandes de façon asynchrone. Le retour ajoute donc `VerificationPending=true` et `NextRead=debug_state` quand l'effet n'est pas encore visible, sans attente bloquante. Pour `toggle_breakpoint`, `VerificationPending=false` et `Unverified` restent permanents tant qu'aucun inventaire fiable des points d'arrêt n'est disponible.

La première sonde `TypeDescriptor.GetEvents` a retourné zéro événement dans Excel pour UserForm, CommandButton et Label alors que `CreateEventProc` avait créé `UserForm_Initialize` et `cmdProbe_Click` : elle ne couvre pas les sources COM de MSForms. `form_event_catalog` lit maintenant le coclass `IProvideClassInfo` et ses interfaces `ITypeInfo` marquées `IMPLTYPEFLAG_FSOURCE` ; chaque événement identifié porte nom, DISPID, interface source et nombre de paramètres, sans prétendre fournir la signature VBA. Essai Excel réel : 16 événements de `FormEvents`, 13 de CommandButton, 8 de Label, sans erreur COM. `Initialize` manque dans `FormEvents` bien que son stub ait été créé dans ce même VBE. La réponse distingue donc `Catalog.SourceInterfacesComplete` de `Catalog.VbeEventCatalogComplete=false` et décrit sa portée. Le catalogue COM est une aide à la découverte ; `CreateEventProc` valide le nom demandé, y compris des événements documentés séparément par VBA. [Documentation Microsoft IProvideClassInfo](https://learn.microsoft.com/en-us/windows/win32/com/using-iprovideclassinfo), [ITypeInfo .NET](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.comtypes.itypeinfo?view=netframework-4.8.1), [Initialize VBA](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/initialize-event).

Premier essai Excel : `project_properties` a renvoyé 16 propriétés, deux composants document et quatre références avec une version stable. `component_properties` sur un composant document a bloqué la passerelle. La sonde `component_probe` a isolé le getter `MailEnvelope` parmi les 70 propriétés de Feuil1 : les 58 getters qui le précèdent ont été testés ; les suivants ne l'ont pas été. Ces 70 propriétés appartiennent à l'objet hôte Excel Worksheet et sont maintenant classées `HostProperties`, séparées des métadonnées communes du `VBComponent` lues via ses descripteurs. La lecture groupée d'un composant document énumère leurs noms sans appeler les getters ; `component_property_value` permet une lecture ciblée et refuse `MailEnvelope` avant l'appel COM. Les autres propriétés objet sont listées sans déréférencement automatique. Le nouveau parcours a répondu dans Excel pour Feuil1 (70 noms hôte) et ThisWorkbook (140 noms hôte), avec révisions stables ; `MailEnvelope` est refusée sans bloquer la passerelle.

`list_references` lit les références réellement sélectionnées dans le projet via `VBProject.References` : nom, GUID, version, chemin si accessible et état cassé. `add_reference_guid`, `add_reference_file` et `remove_reference` utilisent l'empreinte renvoyée par cette lecture, exigent le mode conception et relisent la collection après action. Un chemin de fichier doit avoir été fourni explicitement par l'utilisateur ; les octets de la bibliothèque ne sont pas envoyés au modèle. L'ajout puis le retrait d'une référence Scripting par GUID ont été vérifiés dans un classeur Excel jetable : la collection et son empreinte sont revenues exactement à l'état initial. L'ajout par fichier reste à éprouver. [Documentation Microsoft VBIDE](https://learn.microsoft.com/en-us/office/vba/language/reference/visual-basic-add-in-model/collections-visual-basic-add-in-model).

Lectures : `status`, `list_projects`, `list_modules`, `read_module`, `list_forms`, `form_state`, `form_tree`, `form_properties`, `form_control_properties`. Les lectures de propriétés exposent types, valeurs disponibles, statut de lecture seule et éventuelles erreurs COM. `form_tree` énumère les contrôles imbriqués des Frames et pages de MultiPage, ainsi que les onglets de TabStrip, avec chemins et empreinte de l'arbre. `open_form` ouvre le concepteur. `read_user_file` peut lire au plus 64 Kio de texte à un chemin absolu littéralement fourni par l'utilisateur : une confirmation distincte indique le fournisseur destinataire avant la lecture et la transmission. Modifications : `replace_lines`, `create_module`, `create_class`, `create_form`, `set_form_property`, `set_form_picture`, `add_form_control`, `rename_form_control`, `set_form_control_caption`, `set_form_control_font`, `set_form_control_geometry`. `set_form_picture` charge localement un chemin d'image explicitement fourni ; elle ne transmet pas les octets de l'image au fournisseur.

Chaque fonction possède un schéma d'arguments. Le complément rejette les fonctions inconnues, les paramètres inconnus et les paramètres obligatoires manquants. Configuration offre trois modes indépendants du niveau de raisonnement : **Lecture seule** refuse les écritures VBE, **Demander à chaque action** affiche les arguments et demande une validation, **Automatique** exécute les écritures sans dialogue. Automatique est le défaut des nouvelles installations ; un ancien fichier de configuration sans ce réglage conserve Demander à chaque action jusqu'au choix explicite de l'utilisateur. `read_user_file` garde sa confirmation distincte dans tous les modes. `replace_lines` vérifie l'empreinte SHA-256 du module ; les modifications de formulaire vérifient la version du formulaire et le mode conception. Les résultats sont relus par `VbeSession` et renvoyés au modèle.

Quand l'utilisateur envoie une demande, son texte, les résultats des lectures et l'historique de la conversation sont transmis au fournisseur choisi. En particulier, `read_module` transmet le code VBA au fournisseur. Aucune demande n'est envoyée automatiquement à l'ouverture du VBE.

## Vérification et limites

Le build .NET Framework 4.8 x64 a réussi dans une sortie isolée du worktree. Le parsing des tableaux de réponses JSON a été vérifié avec `JavaScriptSerializer` sous Windows PowerShell 5.1. Un essai direct du CLI local `codex-cli 0.156.1` a confirmé la connexion ChatGPT et l'appel d'un outil dynamique `vbe_status`, suivi de `turn/completed`. Un smoke test du nouveau client .NET en processus GUI sans console a ensuite confirmé `initialize`, `account/read` et `thread/start` avec outils dynamiques. Le test a découvert puis corrigé un BOM UTF-8 émis par `Process.StandardInput` en .NET Framework. L'interface WinForms, les menus natifs, le choix de modèle et d'effort, un tour Codex réel, les créations module/classe/formulaire, les modes Automatique et Lecture seule, plusieurs propriétés scalaires de UserForm, `Font.Name` et `set_form_picture` avec un BMP jetable ont été vérifiés dans Excel. La propriété Picture et la version du formulaire sont restées stables à deux relectures consécutives. La lecture `form_tree` a été vérifiée sur des conteneurs Frame, MultiPage et TabStrip sans contrôle enfant. L'ouverture de la fenêtre est protégée : un échec de l'UI est journalisé sans couper la passerelle existante.

La conversation est hébergée dans un panneau VBE ancré, validé à droite dans Excel après configuration initiale de la disposition. Claude, GitHub Copilot et Gemini ne sont pas implémentés. Les propriétés d'objet et la hiérarchie des contrôles MSForms ne sont pas encore entièrement éditables. La couverture des outils VBE reste progressive ; voir `docs/vbe-coverage.md`.
